# 为什么需要认证
- 防止未授权用户访问敏感数据
- 区分不同用户的权限（普通用户 vs 管理员）
- 记录操作日志（谁在什么时候做了什么）

---

# 常见认证方式

## 1. Basic Auth
- 原理：将 `用户名:密码` 进行 Base64 编码后放在请求头
- 请求头：`Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=`
- 特点：简单但不安全（Base64可解码），通常配合HTTPS使用
- 适用：内部系统、简单场景

## 2. Token（JWT）
- 原理：登录后服务器返回一个token，后续请求携带这个token
- 请求头：`Authorization: Bearer eyJhbGciOiJIUz...`
- 流程：登录接口获取token → 后续请求Header带上token
- 特点：无状态，服务器不需要存session
- JWT结构：Header.Payload.Signature（三段用 `.` 连接）

## 3. Cookie / Session
- 原理：登录后服务器创建session，返回session ID存在cookie中
- 流程：登录 → 服务器返回 `Set-Cookie` → 浏览器自动带cookie
- 特点：有状态，服务器需要存储session信息
- 适用：传统Web应用

## 4. OAuth2
- 原理：第三方授权协议，用户授权后获取 access_token
- 流程：跳转授权页 → 用户同意 → 获取授权码 → 换取token
- 适用：第三方登录（如GitHub登录、Google登录）

## 5. Personal Access Token（PAT）
- 原理：用户在设置中生成一个长期有效的token
- 请求头：`Authorization: Bearer <pat-token>`
- 特点：不需要走登录流程，直接使用
- **Halo使用这种方式**：在后台"个人中心" → "个人令牌"中生成

# 在Postman中配置认证

### 方式一：直接在Header中添加
- 手动添加 `Authorization` 请求头

### 方式二：使用Auth标签页
- 选择认证类型（Basic Auth / Bearer Token / OAuth2）
- 填入对应的凭据
- Postman自动生成Header

### 方式三：集合级别配置
- 在Collection层面设置认证，所有请求自动继承
- 避免每个请求重复配置

# 认证相关的测试点
- 不带认证信息 → 应返回 401
- 带错误的token → 应返回 401
- 带过期的token → 应返回 401
- 普通用户访问管理员接口 → 应返回 403
- 正确认证 → 应返回 200 + 正确数据
